# Существующие решения для AI-разработки Minecraft-модов

Дата проверки: **2026-11-06**.

## Метод и границы доказательств

Проверены первичные источники: исходный код, лицензии, история коммитов, официальная документация, примеры сгенерированных файлов и страницы продуктов. Продукты и генераторы **не запускались**, сгенерированные проекты **не собирались** в рамках этого исследования.

Обозначения в таблицах:

- **К** — возможность подтверждена исходным кодом, конфигурацией или инспектируемым артефактом. Это не означает, что код выполнялся нами.
- **Д** — есть конкретная первичная документация или описанный производителем workflow, но нет публичной реализации либо независимого runtime-теста.
- **М** — есть только маркетинговое обещание без инспектируемой реализации или артефакта.
- **част.** — возможность существует в узких рамках, указанных в ячейке.
- **—** — подтверждение не найдено либо функция вне назначения инструмента.

«Модель» отделена от текстовых ресурсов: это JSON-геометрия, Java/ Bedrock-geometry, Blockbench-модель или item/block model, а не только запись в манифесте. «Запуск» отделен от сборки: запуск клиента, GameTest, проверка поведения и визуальная проверка не считаются эквивалентами.

## Краткий вывод

1. **AI-mod creator** ближе всего к полному детерминированному циклу: prompt → структурированные операции → Java/resources → Gradle → проверки внутри Minecraft → транзакционное сохранение. Его предел — простые предметы, инструменты, еда, блоки и рецепты на Minecraft 1.21.1; текстуры являются заглушками.
2. **Universal Modder** содержит наиболее зрелые открытые agent-методы для recon, вертикального среза, asset pipeline, screenshots и проверки в реальной игре. Это универсальный набор skills/CLI, а не версионно-безопасный Minecraft generator: Minecraft-совместимость и производственный JAR остаются ответственностью agent и target toolchain.
3. **MCreator в ветке `master` уже имеет нативный MCP** со schema-first редактированием workspace, созданием текстур из слоев, Gradle build, запуском клиента и чтением консоли/логов. Это важнее старого стороннего MCreator AI Plugin. Наличие MCP в `master` нельзя автоматически приписывать стабильным релизам.
4. **Player Games и Foundry** документируют не только build/auto-fix, но и runtime-этап: Player — server boot перед выдачей JAR, Foundry — запуск Minecraft и Paper test server с клиентом. Это сильнее compile-only обещаний, но все еще не произвольные behavior assertions или визуальная проверка. Spaleforce и Kodari документируют только build/repair; у всех четырех закрытых решений нет публичной реализации.
5. **Mine Mod AI** честно ограничивает область генерации и публикует границы проверки. Его Fabric-экспорт поддерживает только отдельные custom items на 1.21.1; representative CI не является тестом каждого скачанного результата.
6. Не найдено специализированного открытого решения, которое одновременно дает произвольный version-safe scaffold, качественные Minecraft-native модели/текстуры, client/server behavior tests и визуальную проверку в игре. Рационально соединить Universal Modder orchestration, официальные MDK, MCreator/Blockbench MCP, Gradle/GameTest и evidence-reporting, а не писать еще один текстовый генератор проектов.

### Маркетинг и ограничения, которые нельзя потерять

- **AI-mod creator:** фраза “if AMC says it works, it works” шире доказанной области. Репозиторий сам ограничивает запросы простым контентом, называет проект early alpha и рекомендует fresh test world. Его in-game assertions не проверяют художественное качество текстур или моделей.
- **Universal Modder:** skills и CLI подтверждают наличие методов, но не успешный результат для любого мода. Knowledge-base notes являются отчетами авторов/agents, а не независимым аудитом. Например, Bloons TD6 note прямо оставляет непроверенными two-human session, production performance, shaders и часть production runs. fal/Sprixen/Voidless — внешние сервисы со своими ключами, ценой и условиями; MIT не покрывает их output или игровые assets.
- **AI MC Mods Generator:** “directly buildable” не подтверждено автоматической сборкой. В архитектуре автосборка указана как расширение. Некоторые версии имеют `approximate: true`, а часть ссылок версий ведет на сторонние сайты, поэтому реестр нельзя считать авторитетной compatibility matrix.
- **MCreator AI Plugin:** “professional”, “balanced”, “always current” и “robust recovery” — маркетинг. README ведет установку и clone на другой репозиторий. В `master` после `getPromptAnalysisFromProperties()` в `TextureGenerator.java` видны операторы вне метода; это еще одна причина не считать исходник доказательством работающей сборки. Точная совместимость с MCreator не установлена.
- **Mine Mod AI:** “compile-ready” подкреплено CI образца, а не всеми возможными запросами. Игровые результаты от 2026-10-24 относятся к Java 1.21.11 и Bedrock 1.21.90 и конкретным representative packs; они не подтверждают текущий arbitrary request, клиентскую графику или установку на физическом устройстве.
- **Player Games:** server boot проверяет загрузку, а не заявленную механику, баланс, multiplayer interactions или visuals. Показатели **98.2%** и **13m26s** публикуются самим сервисом без инспектируемого dataset. “All mods are safe” — **М**; source review и server boot не доказывают безопасность. Примеры community builds показывают отдельные версии, но не полную compatibility matrix.
- **Foundry:** “production-quality”, “builds it right” и обычные 1–2 repair attempts — **Д/М** производителя, не независимый benchmark. Home обещает port между Fabric и NeoForge, а Features называет cross-platform porting **coming soon**; поддерживать его сейчас нельзя. Guide создает placeholder texture. Paper validation полезна для dead commands/listeners/defaults, но не заменяет произвольные behavior и visual tests.
- **Kodari:** “60,000+ projects”, “~5 sec” и “~100% build success” — **М**, неаудированные показатели. “All versions” означает перечисленные targets, а не каждый промежуточный релиз. Product page упоминает NeoForge 1.21.1, более свежий NeoForge guide перечисляет только 26.2 и 26.1.2.
- **Spaleforce / Kodari:** возврат compiler errors в AI — конкретный **Д**-workflow, но без публичного кода или воспроизводимого отчета. Даже успешный JAR не доказывает корректную механику, отсутствие server-only crash или качество visuals.
- **Codella:** официальная страница подтверждает только **Д**-workflow source + cloud compile. Заявленные в обзоре CreativeMode stress-testing 100+ players, under 50 ms и 30% compatibility issues на ней не раскрыты. 3D models и textures относятся к отдельному product mode; нельзя автоматически приписывать их каждому server plugin.
- **CreativeMode:** “fully playable”, сложные модели, текстуры, транспорт и превосходство над другими инструментами — **М** без публичного per-request validation evidence.
- **[Обзор “Top AI Minecraft Modding Tools in 2026” от CreativeMode](https://creativemode.net/blog/top-ai-minecraft-modding-tools-in-2026):** это vendor-authored статья, которая ставит собственный продукт первым, а не независимое сравнение. Цифры “40% faster” для MCreator, “65% boilerplate”, “500+ extensions”, “2–3x” для Copilot и stress/latency/compatibility metrics для Codella не сопровождаются ссылками на измерения и относятся к **М**. Copilot — generic coding assistant, а не Minecraft-specific end-to-end generator. Для Codella в таблице использована отдельная официальная страница, а не выводы обзора.

### Важные лицензионные различия

- **MIT/Apache/CC0:** можно переиспользовать код при сохранении требуемых notices; Apache-2.0 также содержит patent и NOTICE условия. Веса Gemma у AI-mod creator не покрываются Apache-2.0.
- **LGPL-2.1:** использование Forge/NeoForge build tools не назначает лицензию новому моду. Модификация и распространение самих инструментов требует отдельного соблюдения LGPL. Forge отдельно предупреждает о MCP data и third-party notices.
- **GPL-3.0 MCreator:** исключение для `*.ftl` разрешает larger work с output шаблонов на выбранных условиях, если этот результат сам не является code-generation template. Нельзя распространять это исключение на весь MCreator core, trademark или brand assets.
- **Blockbench:** GPL покрывает source, но README прямо разрешает proprietary/open/paid external plugins и оставляет созданные модели, текстуры, анимации и screenshots автору.
- **AGPL-3.0 BlockPixel Studio:** копирование postprocess кода в сетевой или распространяемый plugin требует анализа AGPL-обязательств. Ниже предлагается переиспользовать алгоритмический прием, а не копировать файл.
- **MPL-2.0 Architectury:** действует file-level copyleft для covered generator code. Лицензия текущего generated output из источников не установлена; wholesale redistribution требует отдельной проверки. Старое CC0-заявление для legacy templates не переносится на current generator.
- Публичный репозиторий без `LICENSE` не равен open source. В частности, не следует путать MIT-лицензированные **NeoForge MDK mirrors** с отдельным [web `mod-generator`](https://github.com/neoforged/mod-generator), в котором на дату исследования license file не обнаружен.
- Лицензия template/build tool не выбирает лицензию мода автоматически. Mojang mappings, MCP data, Minecraft assets, model weights, third-party plugins и импортированные textures проверяются отдельно.

## 3. Методы, которые стоит переиспользовать

### 3.1 Спецификация и детерминированная генерация

1. **LLM выбирает операции, engine пишет код.** Взять из AI-mod creator промежуточный MCL-like слой: типизированные операции, JSON Schema, validation против текущего состояния, детерминированный generator. Это уменьшает свободную галлюцинацию файлов и делает diff воспроизводимым. Источник: [AI-mod creator README](https://github.com/sjdthree/ai-mod-creator).
2. **Транзакционное состояние.** Сохранять изменение только после выбранных checks; failed request оставляет last-good state, refine и undo работают на snapshots. Источник: [AMC User Guide](https://raw.githubusercontent.com/sjdthree/ai-mod-creator/main/docs/USER_GUIDE.md). Код — Apache-2.0.
3. **Строгий файловый контракт и безопасные пути.** Из AI MC Mods Generator: JSON `{path, content}`, запрет absolute/`..`/NUL, allowlist расширений, лимиты, warnings для неподдержанного. Источник: [schema](https://raw.githubusercontent.com/hcyinnn/ai-mcmods-generator/main/prompts/output_schema.md), [ProjectBuilder](https://raw.githubusercontent.com/hcyinnn/ai-mcmods-generator/main/backend/app/project_builder.py). Код — MIT.
4. **Версии подставляет программа, не LLM.** Переиспользовать placeholder isolation из [ProjectBuilder](https://raw.githubusercontent.com/hcyinnn/ai-mcmods-generator/main/backend/app/project_builder.py), но не переносить его approximate registry. Источником pins должны быть exact target-version MDK и официальные metadata.
5. **Отказ вместо фиктивной реализации.** Из Mine Mod AI: whitelist-спецификация, bounded parameters и явный unsupported result. Не выдавать datapack или shared quadruped за выполненный arbitrary mod request. Источник: [about](https://www.minemodai.com/about). Метод, не код закрытой платформы.

### 3.2 Шаблоны и сборка

6. **Узкий официальный baseline для каждого target.** Fabric only — CC0 example mod; NeoForge only — MIT target-version MDK; Forge only — version-matched Forge MDK. Не смешивать `gradle.properties`, mappings и Java targets разных веток.
7. **Multi-loader через common/platform boundaries.** Из Architectury: `common`, отдельные loader modules, `development*` и `transformProduction*`, а не копирование общих классов в каждый JAR. Генератор — MPL-2.0; лицензию output проверить до копирования.
8. **Сохранять штатные source sets и runs.** Fabric `splitEnvironmentSourceSets()` ловит client-only references при компиляции; NeoForge/Forge MDK уже дают client/server/GameTest/data. Использовать их вместо параллельной launch-системы. Источники: [Loom](https://docs.fabricmc.net/develop/loom/), [NeoForge MDK build](https://raw.githubusercontent.com/NeoForgeMDKs/MDK-26.3-ModDevGradle/main/build.gradle), [Forge guide](https://docs.minecraftforge.net/en/latest/gettingstarted/).
9. **Datagen как единый путь ресурсов.** Складывать generated resources в предусмотренные source sets. Хранить `.bbmodel` как source asset и исключать из production resources, как в [NeoForge MDK](https://raw.githubusercontent.com/NeoForgeMDKs/MDK-26.3-ModDevGradle/main/build.gradle).
10. **Статические проверки до запуска.** Перенести подход MinecraftDev: проверять metadata references, entrypoints, Mixin targets, AT/AW и переводы до дорогого Gradle/game запуска. Custom template finalizers могут делать Gradle import, run configs и tasks. Код — LGPL-3.0-only; проще использовать plugin как внешний инструмент или реализовать нужные проверки самостоятельно.

### 3.3 AI-ready workspace, модели и текстуры

11. **Schema-first tool protocol MCreator.** Перед mod element mutation получать schema; имена брать только из workspace/datalists; не редактировать generated files unlocked elements; после изменений вызывать build и читать console/logs. Для OMP логично вызывать нативный MCP как внешний инструмент, а не копировать GPL core. Источник: [MCreatorMcp.java](https://raw.githubusercontent.com/MCreator/MCreator/master/src/main/java/net/mcreator/ui/mcp/MCreatorMcp.java).
12. **Blockbench как editor, MCP как узкий bridge.** Переиспользовать local stdio MCP → loopback plugin bridge, typed tools и возврат image content. Модельный цикл: blockout → complexity audit → texture → rig check → animation measurements → multi-view screenshots → human review. Источник: [Blockbench MCP](https://github.com/sosadly/blockbench-mcp). MCP — MIT; Blockbench external plugin exception подтверждена.
13. **Objective visual gates вместо самооценки LLM.** Полезны `check_model`, `check_sides`, `check_rig`, `analyze_animation`, reference silhouette IoU и labeled views. Timeout/pending не считать approval. Источник: [tools.ts](https://raw.githubusercontent.com/sosadly/blockbench-mcp/main/src/tools.ts).
14. **Согласованность texture set через style reference.** Из BlockPixel Studio: сначала style sheet, затем reference-guided items и сравнение original/processed. Для game-ready postprocess методически полезны edge-connected chroma-key removal, alpha-bounds crop, nearest-neighbor resize и прозрачный padding. Источник: [postprocess.ts](https://raw.githubusercontent.com/JunDev76/blockpixel-studio/main/server/lib/postprocess.ts). Код AGPL — реализовывать метод самостоятельно либо соблюдать AGPL.
15. **Проверять export format, а не предполагать.** До генерации выбирать Java/Bedrock/GeckoLib codec и учитывать ограничения UV, rotation, multiple textures и animation из [Blockbench format matrix](https://blockbench.net/wiki/blockbench/formats/). Format support не записывать как Fabric/Forge/NeoForge support.

### 3.4 Проверка и честный результат

16. **Разделить четыре уровня evidence:** файлы структурно валидны; Gradle build passed; client/server behavior tests passed; visuals reviewed. Representative CI нельзя выдавать за проверку текущего запроса — хороший контрпример границ дан у [Mine Mod AI validation](https://www.minemodai.com/validation).
17. **Compiler loop — bounded и наблюдаемый.** Spaleforce/Kodari предлагают возврат compiler errors в LLM; у Kodari предел 3 попытки. Для плагина сохранять исходную ошибку, minimized diff и результат каждой попытки. После compile budget исчерпан — остановиться с last-good state, а не объявлять успех. Это метод из **Д**-описаний, не подтвержденный публичный код.
18. **GameTest и dedicated server обязательны там, где применимо.** MDK уже содержат GameTestServer. Проверять не только client launch, но и server load для client-only mods; Forge и NeoForge прямо рекомендуют dedicated-server testing.
19. **Evidence manifest для каждого артефакта:** MC/loader/mappings/Java pins, template commit, команды, build logs, tests, screenshots, измененные файлы, warnings и непроверенные области. Никаких “100% working” без соответствующего scope.

### 3.5 Runtime-orchestration из Universal Modder и hosted studios

20. **Сначала recon и существующие field notes.** Перед кодом определять engine, точную версию, loader, anti-cheat, save folders и дешевый route; читать заметки с exact versions и gotchas. После работы записывать route, verification и unresolved facts в knowledge base. Источники: [mod-any-game](https://raw.githubusercontent.com/rehan-remade/universal-modder/main/skills/mod-any-game/SKILL.md), [Minecraft playbook](https://raw.githubusercontent.com/rehan-remade/universal-modder/main/skills/mod-any-game/references/engines/minecraft.md). Репозиторий — MIT.
21. **Один vertical slice до масштабирования.** Провести один item/mechanic через placeholder assets, запуск, logs и screenshot; только затем расширять мод. Каждый рабочий шаг фиксировать. Это уменьшает объем неработающего AI-кода по сравнению с генерацией всего проекта сразу.
22. **Безопасная лаборатория и восстановление.** До запуска делать `um backup`, использовать отдельный profile/world и восстанавливать pristine state перед повторным сценарием. Для нашего плагина объединить это с project snapshots и last-good transactions.
23. **Реальная игра как oracle.** Повторяемый сценарий: launch → deterministic scene → действие → screenshot + logs → решение. Использовать фиксированный window size, mod-side test commands или loopback JSON bridge вместо нестабильных menu clicks. После трех одинаковых неудач останавливаться и менять подход. Источник: [game-automation](https://raw.githubusercontent.com/rehan-remade/universal-modder/main/skills/game-automation/SKILL.md).
24. **Разделять offline и live-game workers.** Offline worker изучает source, пишет generators и unit tests; единственный game worker выполняет build/deploy/launch/probe; orchestrator проверяет claims по logs/files. Это предотвращает параллельные Gradle runs и противоречивые runtime actions. Источник: [agent roles](https://github.com/rehan-remade/universal-modder#whats-inside).
25. **Проверять production artifact, не только dev run.** Universal Modder фиксирует случай, когда Mojang-name benches проходят, а SRG production JAR падает. В acceptance добавить отдельный запуск упакованного JAR на реальном instance и протокол version check для multiplayer. Источник: [Bloons TD6 field note](https://raw.githubusercontent.com/rehan-remade/universal-modder/main/knowledge/games/minecraft/bloons-td-6-in-minecraft.md).
26. **Generation manifest и publish lint.** Записывать каждый asset generation и блокировать случайную публикацию game files, decompiled source и secrets (`um publish check`). Это дополняет license/provenance manifest нашего плагина. Источники: [README](https://github.com/rehan-remade/universal-modder), [asset-pipeline](https://raw.githubusercontent.com/rehan-remade/universal-modder/main/skills/asset-pipeline/SKILL.md).
27. **Source-grounded generation и boot gate.** У Foundry полезен **Д**-подход: AI ищет API в decompiled source выбранной версии рядом с проектом. У Player Games — compile и server boot до разблокировки download. У Foundry Paper дополнительно проверяются dead commands, unregistered listeners и missing config defaults. Перенять эти gates, но не выдавать boot за behavior proof. Источники: [Foundry features](https://foundry.archreon.com/features), [Foundry changelog](https://foundry.archreon.com/changelog), [Player validation](https://www.player.games/en-US/ai-minecraft-mod-maker).

## 4. Пробелы, которые должен закрыть наш плагин

### P0 — основной путь

1. **Стадия дизайна до кода.** Нужны идея/уточнения, gameplay loop, зависимости контента, численные параметры, client/server side и acceptance criteria. Universal Modder добавляет intake/recon, но не typed gameplay specification; остальные обычно начинают сразу с prompt → files, а AMC и Mine Mod AI покрывают только узкий structured subset.
2. **Доказуемая compatibility matrix.** Для каждого `(MC, loader, mappings, Java)` хранить exact MDK/template source и статус проверки. Не объявлять поддержку всех комбинаций по одному списку MC versions и трем loader prompts.
3. **Единая спецификация как источник всех артефактов.** Java, lang, recipes, loot, blockstates, models, textures, animations и tests должны ссылаться на одни IDs и acceptance criteria. Нужна проверка broken references до сборки.
4. **Детерминированный scaffold + ограниченный AI delta.** Официальный MDK создает toolchain; AI меняет только спецификацию и необходимые файлы. Это закрывает разрыв между свободной LLM-генерацией и поддерживаемыми официальными шаблонами.
5. **Build → diagnose → repair → rebuild.** Нужен bounded loop с реальными Gradle errors, MinecraftDev-like static checks и source/API lookup выбранной версии. Prompt-only anti-hallucination checklist недостаточен.
6. **Runtime behavior verification.** Запускать client и dedicated server, GameTest/автоматизированные сценарии для заявленной механики, собирать crash reports и отличать startup success от behavior success. Адаптировать Universal Modder oracle/JSON bridge и production-JAR проверку, а не ограничиваться MCreator logs или Player/Foundry boot gates.
7. **Визуальная проверка именно в Minecraft.** Blockbench screenshots проверяют asset, но не шейдеры, scale, display transforms, missing texture, particles, GUI, lighting или animations в игре. Нужны deterministic world/camera, screenshots нескольких ракурсов и состояний, image review и human gate. `um win shot/drive` и repeatable scenes Universal Modder дают готовый метод, но требуют Minecraft-specific сценариев и assertions.
8. **Полный asset pipeline.** Согласованные AI textures, прозрачность/tileability/size checks, item/block models, entity geometry, UV, rigging, animation, export, namespace placement и code registration. Сейчас эти части разрознены между BlockPixel, Blockbench MCP, MCreator и Java generators.

### P1 — качество и эксплуатация

9. **Last-good transactions и rollback.** Любой failed build/runtime/visual check должен сохранять предыдущий рабочий проект. Refine обязан показывать diff спецификации и файлов. Совместить project snapshots AMC с `um backup` и pristine test worlds Universal Modder.
10. **Доказательства вместо маркетинга.** Плагин обязан выдавать отчет “что проверено / чем / на какой версии / что осталось неизвестным”. Сохранять knowledge note с route и gotchas по образцу Universal Modder. Никаких безусловных “working”, “all versions” или “100% success”.
11. **Визуальный regression baseline.** Сохранять reference screenshots и сравнивать refine с предыдущим approved результатом, чтобы исправление Java не ломало модель, UV или display settings незаметно.
12. **Лицензии и provenance.** Для каждого template, generated asset, model weight и third-party dependency фиксировать источник и условия. Не смешивать AGPL/GPL код с permissive plugin без осознанного решения.
13. **Безопасное выполнение сгенерированного кода.** Gradle и Minecraft запускают недоверенный сгенерированный код. Нужны отдельный workspace, минимальные permissions, контроль сети/секретов, timeout и отсутствие доступа к пользовательским файлам вне проекта. Path allowlist из hcyinnn решает только часть угрозы.
14. **Интеграция с существующими MCP, а не дублирование.** MCreator MCP закрывает schema-driven workspace/build/client logs; Blockbench MCP закрывает asset authoring/review. Плагину нужен общий orchestration и evidence model, включая случаи, когда инструмент недоступен — без ложного fallback “готово”.

## Рекомендуемая основа спецификации

Базовый путь: **SDD spec + recon → exact official MDK → typed operations → static checks → Gradle build → GameTest/client/server scenarios → Blockbench и in-game visual review → bounded repair → evidence manifest → export**. Из Universal Modder взять `MODLOG`/knowledge notes, backups, vertical slice, offline/game worker split, `um win` screenshots и production-JAR oracle. Для multi-loader добавлять Architectury common/platform только при реальной необходимости; для одного loader использовать его официальный MDK. Такой состав закрывает подтвержденные пробелы и переиспользует существующие инструменты без зависимости от маркетинговых обещаний hosted-сервисов.
